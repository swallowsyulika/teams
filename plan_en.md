# User Requirements Document (URD): Multi-Agent Collaboration Development Team

## 1. Product Overview

This system aims to build a highly scalable, automated software development team utilizing the LangGraph and LangChain frameworks. Through a Supervisor (Leader) and Worker (Experts) architecture, the system achieves requirements analysis, task breakdown, asynchronous parallel development for frontend and backend, and strict automated code reviews, ultimately delivering a software project that meets user expectations.

## 2. System Architecture & Workflow

The system execution is divided into two main phases to ensure architectural stability and parallel development efficiency:

* **Phase 1: System Initialization**
1. The user inputs the original requirements.
2. The **Planner** designs the system architecture and breaks down the tasks.
3. The **Reviewer** audits the Planner's proposal. If passed, it proceeds to Phase 2; if failed, it is returned for revision.


* **Phase 2: Asynchronous Parallel Execution**
1. The **Leader** reads the global state, breaks down the task list into the smallest "sub-tasks," and dispatches them independently to domain experts (e.g., Frontend Task 1, Backend Task 1).
2. **Experts (Frontend/Backend)** work asynchronously and in parallel within a sandbox environment, without waiting for each other.
3. Upon completing a sub-task, the Expert submits it directly to the **Reviewer** for validation.
4. **Reviewer Pass**: Updates the state to completed and routes back to the Leader to dispatch the next sub-task.
5. **Reviewer Fail**: Attaches specific modification feedback and returns it directly to the original Expert for correction (triggering a local loop).



## 3. Agent Roles & Responsibilities

| Role (Agent) | Core Responsibilities | Behavioral Guidelines & Constraints |
| --- | --- | --- |
| **Planner** | System planning & task breakdown | Responsible for outputting system architecture and frontend/backend task lists. Task granularity must be extremely small to ensure completion in a single generation. |
| **Leader** | Task dispatching & progress tracking | Does not write code. Only responsible for reading the State, determining current progress, and dispatching "only one" sub-task at a time to the corresponding Expert. |
| **Expert (Frontend)** | Frontend code implementation | Receives a single sub-task, uses tools to read/write code and test. Submits to the Reviewer upon completion. |
| **Expert (Backend)** | Backend code implementation | Receives a single sub-task, uses tools to read/write code and test. Submits to the Reviewer upon completion. |
| **Reviewer** | Strict gatekeeping & code review | Checks for logic errors, malicious code, and task completion. Never compromises; fails and returns with precise feedback immediately upon finding errors. |

*(Note: Expert nodes are designed with a pluggable interface, allowing seamless future expansion for roles like Database Expert or DevOps Expert.)*

## 4. Global Graph State Management

To prevent infinite loops and state confusion, all Agents are stateless and strictly rely on the following structured Graph State for routing:

* `original_requirement` (String): The user's initial request.
* `system_design` (Dict): System configuration and architecture generated by the Planner.
* `task_list` (List[Dict]): Global task list containing each sub-task's ID, description, domain, and current status (`pending`, `in_progress`, `completed`).
* `current_active_tasks` (Dict): Records the currently executing sub-task IDs for each domain (e.g., `{"frontend": "task_2", "backend": "task_1"}`).
* `code_base` (Dict): The current state of the accumulated code or file structure.
* `retry_counters` (Dict): Tracks the number of times each sub-task has been returned by the Reviewer (e.g., `{"task_1": 3}`).
* `current_actor` (String): State machine routing indicator, marking the next Agent to be awakened.

## 5. Communication Protocol & Structured Outputs

Data transfer between nodes strictly enforces structured output constraints using Pydantic (or JSON Schema):

* **PlannerOutput**: Contains `system_architecture`, `frontend_tasks`, `backend_tasks`.
* **LeaderDecision**: Contains `next_actor`, `dispatched_task_id`.
* **ExpertSubmission**: Contains `task_id`, `modified_files`, `tool_execution_summary`.
* **ReviewerEvaluation**: Contains `is_passed` (Boolean), `feedback` (String).

## 6. Tools & Environment

Experts are equipped with basic OS capabilities required to execute tasks. All tools must run in a secure environment:

* `read_file`: Reads the content of a file at a specific path.
* `write_file`: Writes or overwrites code in a file.
* `bash`: Executes terminal commands (e.g., compiling, running tests, installing dependencies).
* **Security Protocol**: All tool executions, especially `bash`, must be restricted to an isolated Docker Container or Sandbox environment to prevent damage to the host system.

## 7. System Guardrails & Edge Cases

* **Circuit Breaker Mechanism**: System global variable `max_retries = 10`. If a single sub-task reaches this retry limit, the Reviewer will intercept it, mark it as failed, and pause that branch's workflow. It will then wait for human intervention or re-evaluation by the Leader, completely preventing infinite loops.
